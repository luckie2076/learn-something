# 阶段五：自动化测试

> 目标：用代码替你守住「改了 A 没搞坏 B」的底线。没有测试的重构是裸奔。
> 本阶段**按测试类型分子目录**，每个目录自带 README 讲清该层的领域知识，并尽量附可运行示例。

## 1. 为什么需要自动化测试

**为什么**：手动点页面验证太慢、太易漏，且无法回归。测试把「预期行为」写成代码，
每次改动后自动跑一遍，几分钟告诉你哪里坏了。它是工程化里**质量保障**的支柱。

## 2. 测试的三层（测试金字塔）

![金字塔]由快到慢、由细到粗：

- **单元测试（Unit）** → [`unit/`](./unit/README.md)：测一个函数 / 类的最小单元。最快最稳，应该最多。
- **组件测试（Component）** → [`component/`](./component/README.md)：测组件渲染与交互（如点击按钮数字 +1）。比单元慢，比 E2E 快。
- **E2E 测试（端到端）** → [`e2e/`](./e2e/README.md)：模拟真实用户在浏览器里的完整操作。最贴近真实，但也最慢、最脆，只覆盖核心流程。

**为什么分层**：单元测试快且稳，应该最多；E2E 珍贵但慢，只覆盖核心流程。这就是「测试金字塔」。

## 3. 覆盖率不是目的

`coverage` 告诉你「多少代码被测试执行过」，但**高覆盖率 ≠ 高质量**。重点测「容易错、容易变」的逻辑，
而不是为了数字去凑无意义的断言。详见 [`unit/`](./unit/README.md)。

## 4. 怎么学这一章

1. 先跑 [`unit/`](./unit/)：最轻量，体验红→绿循环。
2. 再跑 [`component/`](./component/)：理解「以用户行为为中心」的 Testing Library 写法，以及为什么需要 DOM 环境。
3. 最后读 [`e2e/`](./e2e/README.md)：理解它为什么最贵、该用在哪（附 Playwright 范本，但不在通用示例里一键跑——它依赖你的真实业务页面）。

> 三层不是「选边」，而是互补：单元 / 组件做日常兜底，E2E 守核心流程。

## 5. 下一步

把测试接进 CI（阶段七），让每次提交自动跑，才能真正「守住底线」，而不是只在本地跑。
